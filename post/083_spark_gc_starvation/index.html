Debugging the 7-Day Spark Job

Parquet Midpoints, GC Pauses, and Silent Executor Eviction

Sep 16, 2026 7 min read

The Incident: From 3 Hours to 7 Days

Our central Spark ingestion pipeline feeds user-defined feature tables into our Feature Store, powering over 100+ production ML models. It is built to scale to support data science and business users across teams as our feature platform grows.

The job used to take about 3–4 hours. Then it went up to 4 days. Recently, it ran for over 7 days and never finished.

Initial triage checklist:

  • Did we deploy a code change? No. Same commit, same configs.
  • Did data volume surge? No. Row count and data size didn’t significantly increase. (I previously wrote a library which monitors just exactly this.)
  • Is the cluster unhealthy? No. Other teams’ Spark jobs finished normally.
  • Is the Feature Store throttling? No. Write latency and error rate were flat.
  • Did the job fail with an error? No stack traces, no OOM errors, no non-zero exit codes. It just ran forever.

The Spark UI show active execution:

Out of 40 tasks, 39 finished in seconds. 1 task however failed 177 times and kept retrying. Every task failure logged:

ExecutorLostFailure (executor ... exited unrelated to the running tasks)
Reason: Executor killed by driver.

The driver logs showed a heartbeat timeout every ~20 minutes:

Removing executor ... with no recent heartbeats: 149645 ms exceeds timeout 120000 ms

So the driver kept killing executors in an infinite loop.

The job already had 16 GB per executor. The tempting fix, throwing hardware and memory at it (this will surely help 🤞):

--executor-memory 32g --num-executors 100

No. This doesn’t help—it blows up the cloud bill 💵. As we will see, more executors do nothing when only one task has data. More memory only buys time before an unbounded heap fills up again.


Business Impact

The job runs every few hours to update online features. When it stalls, 100+ production models score on stale data, directly hitting pricing predictions.

The goal was to get runtime back under an hour by fixing the real root cause once and for all.


Investigation

1) The Parquet Midpoint Trap

The input was a single ~246 MiB Parquet file. Calling df.rdd.getNumPartitions returned 40, so Spark launched 40 tasks. But per-task metrics made no sense:

One task read all 45,876,936 rows. The other 39 tasks read 0 bytes and finished immediately.

Why?

Parquet files store data in row groups, which form the unit of work for Parquet readers.

Spark doesn’t seem know the total number of row groups when it plans. Getting it would mean opening every file and seeking to the end of each one for its footer. For multiple files on object storage like AWS S3, that can take time. I assume that’s the trade Spark made.

Instead, when Spark plans file splits, it calculates byte ranges based on file metadata via FilePartition.maxSplitBytes:

def maxSplitBytes(sparkSession: SparkSession, selectedPartitions: Seq[PartitionDirectory]): Long = {
  val defaultMaxSplitBytes = sparkSession.sessionState.conf.filesMaxPartitionBytes   // 128 MiB
  val openCostInBytes      = sparkSession.sessionState.conf.filesOpenCostInBytes     // 4 MiB
  val minPartitionNum      = sparkSession.sessionState.conf.filesMinPartitionNum
                               .getOrElse(sparkSession.leafNodeDefaultParallelism)   // 40
  val totalBytes   = selectedPartitions.flatMap(_.files.map(_.getLen + openCostInBytes)).sum
  val bytesPerCore = totalBytes / minPartitionNum
  Math.min(defaultMaxSplitBytes, Math.max(openCostInBytes, bytesPerCore))
}

Each byte range is assigned to 1 task.

The actual read parallelism reckoning comes at read time, when Spark passes a task’s byte range to the Parquet reader in SpecificParquetRecordReaderBase.initialize:

ParquetReadOptions options = HadoopReadOptions
  .builder(configuration, file)
  .withRange(split.getStart(), split.getStart() + split.getLength())  // <-- the whole story
  .build();

At read time, parquet-java determines which task owns a row group using a midpoint test in ParquetMetadataConverter.filterFileMetaDataByMidpoint:

long midPoint = startIndex + totalSize / 2;
if (filter.contains(midPoint)) {
  newRowGroups.add(rowGroup);
}

A task only reads a row group if its byte range covers the row group’s midpoint:

In our case, the parquet file held exactly 1 row group:

This explains why 1 task did all the work, even though 40 tasks were allocated.

2) The Unbounded Future Buffer

The skew explains the imbalance, but it doesn’t explain why an executor with a 16 GB can’t grind through 45.8 million rows however slowly.

So I took a few thread dumps from an executor before dying, and all pointed to:

"Executor task launch worker for task 5.260 in stage 809.0"   RUNNABLE
  scala.concurrent.impl.Promise$DefaultPromise.onComplete(Promise.scala:307)
  scala.concurrent.Future.zipWith(Future.scala:457)
  scala.concurrent.Future$.$anonfun$sequence$1(Future.scala:671)
  scala.collection.LinearSeqOptimized.foldLeft(LinearSeqOptimized.scala:126)
  scala.concurrent.Future$.sequence(Future.scala:671)
  featurestore.util.ConcurrentFutureProcessor$.concurrentMap(ConcurrentFutureProcessor.scala:32)

I tracked it down to concurrentMap in our shared Feature Store library:

def concurrentMap[A, T](items: TraversableOnce[A], maxInFlight: Int, timeout: Duration)(
    task: A => Future[T]
)(implicit ec: ExecutionContext): List[T] = {
  val futures        = ListBuffer[Future[T]]()
  val pendingFutures = ListBuffer[Future[T]]()
  items.foreach { item =>
    val future = task(item)
    futures.append(future)  // <-- Appended forever, never drained
    pendingFutures.append(future)

    // Limit concurrency to maxInFlight
    if (pendingFutures.size >= maxInFlight) {
      pendingFutures.headOption.foreach(Await.ready(_, timeout))
      while (pendingFutures.headOption.exists(_.isCompleted)) pendingFutures.remove(0)
    }
  }

  if (futures.nonEmpty) {
    Await.result(Future.sequence(futures.toList), timeout)  // <-- Allocations
  } else Nil
}

The bug was subtle:

  1. pendingFutures bounded concurrency to maxInFlight and drained completed futures properly.
  2. But futures was never drained. Every future across all 45.8 million rows was appended into a single list and held in memory.
  3. Future.sequence made it worse: it runs a foldLeft calling zipWith, allocating millions more Promise objects.

The implementation bounds concurrency, but not memory

3) Stop-The-World GC Freezes the Heartbeat

The job had no JVM telemetry, so I attached an OpenTelemetry agent to the executors to export JVM metrics to Grafana:

  • Old generation heap usage (jvm.memory.used) constantly climbed at ~700 MiB/min.
  • Old generation usage after collection (jvm.memory.used_after_last_gc) didn’t drop after GC runs. This means the GC cannot reclaim memory because they were still considered live references by the JVM.
  • Minor GC pauses escalated to 51.4 seconds per minute, meaning application threads were frozen by stop-the-world pauses for over 86% of the time.

Spark executors send heartbeats every 10 seconds via a background thread in Heartbeater:

private val heartbeater = ThreadUtils.newDaemonSingleThreadScheduledExecutor(name)
heartbeater.scheduleAtFixedRate(heartbeatTask, initialDelay, intervalMs, TimeUnit.MILLISECONDS)

A long stop-the-world GC pause freezes all JVM threads, including this heartbeater.

On the driver side, HeartbeatReceiver waits up to 120 seconds. When an executor goes silent, the driver assumes it crashed and evicts it:

if (now - lastSeenMs > executorTimeoutMs) {
  logWarning(s"Removing executor $executorId with no recent heartbeats: " +
    s"${now - lastSeenMs} ms exceeds timeout $executorTimeoutMs ms")
  // Asynchronously kill the executor to avoid blocking the current thread
  killExecutorThread.submit(new Runnable {
    override def run(): Unit = Utils.tryLogNonFatalError {
      sc.killAndReplaceExecutor(executorId)

Which is exactly the log we saw:

Removing executor 158 with no recent heartbeats: 149645 ms exceeds timeout 120000 ms

The driver killed the executor, requested a fresh replacement, handed it the exact same task, and watched it freeze and die again—177 times in a row.


The Fix

1) Repartition by Row Count, Not File Bytes

When tasks execute per-record asynchronous calls, work volume is driven by row count, not byte size.

Instead of relying on Spark’s default byte splitting, we explicitly repartition based on target rows:

val targetRowsPerPartition = 1_000_000
val partitions = math.max(1, (rowCount / targetRowsPerPartition).toInt)

df.repartition(partitions)

This breaks any giant row groups into balanced partitions across all executors.

2) Stream with a Semaphore Backpressure

Looking at the call site, the caller only cared about recording failed rows:

val errorRows = df.mapPartitions { rows =>
  val (rows1, rows2) = rows.duplicate
  implicit val ec: ExecutionContextExecutor = scala.concurrent.ExecutionContext.global
  val rowIngestion = RowIngestionSingletonStore(_rowIngestionRegistryId)(...)

  try {
    ConcurrentFutureProcessor
      .concurrentMap(rows1, maxInFlight, timeout) { row =>
        rowIngestion.ingestAsync(row).map(result => (row, result == SendResult.OK))
      }
      .iterator
      .filterNot(_._2)  // <-- Discard successful rows anyway
      .map(_._1)
  } catch {
    case _: TimeoutException => rows2
  }
}(df.encoder).rdd

There was no reason to buffer 45.8 million futures. I replaced it with a bounded streaming worker using a Semaphore, sth like:

def ingestPartitions(
    rows: Iterator[Row],
    rowIngestion: RowIngestion,
    maxInFlight: Int
)(implicit ec: ExecutionContext): Iterator[Row] = {
  val failed   = new ConcurrentLinkedQueue[Row]()
  val inFlight = new Semaphore(maxInFlight)
  val pending  = new AtomicLong(1L)
  val done     = new CountDownLatch(1)

  def onOneDone(): Unit = {
    inFlight.release()
    if (pending.decrementAndGet() == 0L) done.countDown()
  }

  rows.foreach { row =>
    inFlight.acquire() // Blocks reading from iterator when inFlight hits limit
    pending.incrementAndGet()
    try {
      rowIngestion.ingestAsync(row).onComplete {
        case Success(result) if result == SendResult.OK => onOneDone()
        case _ => failed.add(row); onOneDone()
      }
    } catch {
      case NonFatal(_) => failed.add(row); onOneDone()
    }
  }
  onOneDone()

  done.await()
  failed.iterator().asScala
}

val errorRows = df.mapPartitions { rows =>
  ingestPartitions(rows, rowIngestion, maxInFlight)
}(df.encoder).rdd

This ensures:

  • Constant memory footprint: Memory stays fixed at $O(\text{maxInFlight})$ instead of scaling with row count.
  • Young Gen collection: Successful futures complete and are dereferenced immediately, getting garbage-collected in milliseconds without touching Old Gen.

Results

Runtime dropped from hanging indefinitely back to ~1 hour, while cutting executor memory from 16 GB to 8 GB.


Learnings

  • Read parallelism is bounded by row groups: Spark calculates split tasks by byte ranges, but Parquet readers assign work by row group midpoint.
  • The Generational Hypothesis: Most objects die young. Structure code so allocations are consumed and dereferenced immediately, never surviving into Old Generation.
