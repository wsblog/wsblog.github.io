Pricing Experimentation

A look at how we run A/B tests on real-time pricing

Jun 13, 2024 4 min read

When we search for products on an e-commerce, the prices are rarely static. Behind the scenes, hundreds of pricing campaigns run at the same time—special mobile app rates, discounts for specific target, or machine learning models adjusting prices.

Before launching a new pricing campaigns to users, we have to test it first: does this campaign actually bring more values?

This is where pricing experimentation comes in.

Unlike a simple frontend A/B test (like testing a new button color or page layout), experimenting with prices happens deep inside backend services on the live search path. We have to evaluate business rules, assign experiment variants, and calculate prices accordinly.


Requirements

Functional Requirements

  • Campaign & Experiment Management
    • An internal UI tool for business teams to create pricing rules, set up A/B tests, and go through an approval process before anything goes live.
  • Targeting (Segmentation)
    • The ability to target specific user groups based on request details (e.g., users browsing on mobile, users searching from a specific country, or logged-in members).
  • Allocation Strategies
    • Support for splitting traffic by different keys (e.g., by user ID, time, etc).
  • Metrics
    • Collecting data on which users saw which prices so we can measure the business impact (conversion rates, revenue, and margins).

Non-Functional Requirements

  • Low Latency
    • Pricing services handle high request volumes. Checking experiment variant cannot add extra long latency.
  • High Availability & Safety
    • The experimentation system must stay available so A/B experiment is not disrupted.

Campaigns, Allocation, Experiment

What each one means:

  1. Campaign: The actual pricing rule or discount logic (for example, “apply a 5% discount”).
  2. Segment: The target audience eligible for that rule (for example, “mobile users searching in Thailand”).
  3. Experiment: The A/B test setup that splits traffic into groups:
    • Control Group (Variant A): Experiences standard pricing behavior (the baseline).
    • Treatment Group (Variant B): Experiences the new pricing campaign.

Because a single experiment might test multiple campaigns, or a campaign might be reused across tests, we keep them in separate tables linked together:

Figure 1: Database schema separating campaign rules, targeting segments, and experiment configurations.

In this setup:

  • The campaign table stores the pricing logic, schedules, and approval statuses.
  • The segment table holds the targeting rules evaluated against incoming search requests.
  • The experiment table links to an allocation strategy that defines how traffic is split.
  • The campaign_experiment table acts as a bridge, mapping which specific campaigns are activated for each variant.

Deterministic Allocation

Once a search request matches a targeted segment, how do we decide whether a user gets Variant A or Variant B? This process is called allocation.

We cannot query a remote database on every search request to look up or store an assignment—that would add too much latency and introduce a single point of failure. Instead, the service computes the variant locally on the fly using deterministic hashing:

$$\text{bucket} = \text{hash}(\text{entity_id}) \pmod{100}$$

At a high level:

  1. We take an identifier like user_id.
  2. We run it through a fast, uniform hash function and map it into a bucket between 0 and 99.
  3. For a 50/50 test, buckets 0–49 get Variant A (Control), and buckets 50–99 get Variant B (Treatment).

Because this is a stateless mathematical calculation, the same user consistently gets the same variant every time they search without storing anything in a database.

When running 100+ of experiments simultaneously, there are some real-world challenges. A classic one is experiment correlation. Solving these requires more advanced allocation techniques.

Integrating Experiments in the Code

When people first think of A/B testing in code, they usually picture a basic if/else check:

request = get_request()
ctx = get_context(request)

# Simple A/B test check
if experiment_client.determine_variant("EXPERIMENT-ID", ctx) == "B":
    plan_b()  # Variant B: Treatment
else:
    plan_a()  # Variant A: Control

This works well if we only have one or two simple experiments. But in real-world pricing where 100+ of experiments run at the same time across different markets, hardcoding experiment names in code doesn’t work. Every new test would require writing code, testing, and deploying.

Instead, the pricing service uses a rule engine:

request = get_request()
ctx = get_context(request)

# 1. Match request against active campaigns
eligible_campaigns = rule_engine.evaluate(ctx)

# 2. Check experiment variants and apply rules dynamically
for campaign in eligible_campaigns:
    variant = experiment_client.determine_variant(campaign.experiment_id, ctx)
    if variant == "B":
        pricing_calculator.apply_rule(campaign.treatment_rule)
    else:
        pricing_calculator.apply_rule(campaign.control_rule)

With this approach:

  • No deployments needed: Business teams can launch, modify, or stop experiments directly from the internal UI without needing an engineer to deploy code.
  • Handling multiple campaigns: The engine can handle conflict resolution and campaigns stacking.
