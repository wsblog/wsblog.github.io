Data Pipeline Observability

Building a company-wide library for data pipeline observability

Jun 26, 2026 5 min read

The Question

Thousands of data pipelines. Sooner or later, someone has to answer:

For every job, how much data did this run touch, how long did it take, how much did it cost — and how does that compare to yesterday, last week, last month?

Sounds boring. But it’s also the highest-leverage question a platform team can answer: almost every silent pipeline failure shows up first as a change in one of those numbers.


Mapping SRE Golden Signals to Data Pipelines

Google’s SRE framework defines Errors, Traffic, Latency, and Saturation as the foundational metrics for system health.

SignalData Pipeline EquivalentWhat It Catches
ErrorsTask failures & retriesCrashes, OOMs
TrafficRows & bytes (read / written)Volume anomalies, silent drops, and partial writes
LatencyStage & job runtimeSLA breaches, data surges, and join skew
SaturationCPU, Memory spill, JVM GCExecutor starvation and memory pressure

1) Errors

“the rate of requests that fail.”

In data pipelines, the common trap is relying solely on orchestrator exit codes. A Spark job can exit 0 while hundreds of tasks fail and retry under the hood.

Example metrics:

  • failedTasksCount & taskFailureRate: Categorized by reason (ExceptionFailure, FetchFailed, ExecutorLostFailure).

2) Traffic

“a measure of how much demand is being placed on your system.”

For pipelines, demand is data throughput—rows and bytes in and out, tagged by source, direction, and user.

Example metrics:

  • inputBytesRead & inputRecordsRead: Volume per input scan (S3, Kafka, Delta, Iceberg).
  • outputBytesWritten & outputRecordsWritten: Volume delivered to destination sinks.
  • volumeAnomalyRatio: Run-over-run record count vs. a rolling 7-day baseline.

3) Latency

“the time it takes to service a request,” tracked in percentiles rather than simple averages.

For pipelines, it’s total runtime against business SLAs. But high-level duration only becomes actionable when decomposed.

Example metrics:

  • jobDurationMs & stageDurationMs: Wall-clock runtimes per job and stage.
  • taskSkewRatio (maxTaskDuration / p50TaskDuration): Direct indicator of data skew.

4) Saturation

“how full your service is, emphasizing the resources that are most constrained.”

For Spark, this measures executor CPU, JVM memory, disk I/O, and network limits.

Pipelines rarely fail cold; they saturate first. An executor running out of memory doesn’t crash immediately—it thrashes in GC, spills shuffle partitions to disk before finally throwing an OOM.

Example metrics:

  • jvmGCTime & jvmGCRatio (jvmGCTime / executorRunTime): Time spent in garbage collection. >10% signals severe memory pressure.
  • memorySpillBytes & diskSpillBytes: Shuffle data that couldn’t fit in execution memory and spilled to local disk.
  • executorCpuTime vs executorRunTime: Low ratio indicates tasks blocked on I/O wait (S3 throttling, network shuffle, slow databases).

How to Monitor Across Teams

Take traffic as an example. The two obvious approaches both fail.

Anti-Pattern 1: Cron Queries

The naive answer: running scheduled job SELECT COUNT(*), SUM(<byte_size>) FROM <table> against every table we care about.

  • Doesn’t scale to thousands of tables. Every new table is one more entry to maintain.
  • Costs. Scans entire datasets periodically. That bill isn’t free.
  • Not real-time. By the time the cron queries run, the upstream job finished hours ago.
  • Lack of Attribution. A row count reported doesn’t tell which job produced those rows or what it read to produce them.

Anti-Pattern 2: User-Land Application Hooks

The other obvious answer: push instrumentation down to the user, requiring application developers to explicitly instrument code (e.g., calling df.count() prior to writes)

  • Optional instrumentation is forgotten instrumentation. In a platform with hundreds of contributors, “every team should remember to do X” is a hope, not a strategy.
  • df.count() isn’t free. It forces an additional materialization pass over the lineage graph unless cached. Now we’re asking every user to think about caching too, which they’ll get wrong.
  • Governance Friction. Two teams tag their metrics differently and we can’t compare them.

Both fail for the same reason: they push observability work onto the platform’s users, instead of making it a property of the platform.


What I Built: The Telemetry Library

The library takes a different approach: it hooks directly into Spark’s runtime internals to collect telemetry as jobs execute—throughput, stage runtimes, GC pauses, memory spill, and task execution profiles.

Integration is a single registration at application startup:

implicit val spark: SparkSession = SparkSession.builder()
  .appName("my-job")
  .getOrCreate()

val observability = new PlatformObservability(
  metricPrefix = "platform.spark.observability",
)(spark)

observability.register()

What does an application team actually get?

  • One line of code. Register once at session initialization; zero pipeline refactoring.
  • Zero compute overhead. Extracted from Spark runtime internals—no trigger queries, no re-computations, no extra cloud spend.
  • Standardized org-wide. Consistent metrics and tags across hundreds of pipelines.

Metrics are pushed asynchronously to a metrics gateway and visualized in Grafana, backing automated anomaly detection and team dashboards.


Beyond Monitoring: Optimization Hints

The library also flags redundant work: if the same DataFrame is recomputed without an intervening .cache() or .persist(), it emits a warning. Catching duplicate compute directly on the dashboard gives engineers immediate, actionable cost wins.


The Result: A Real Incident

A daily pipeline once finished completely green—exit code zero, all stages succeeded, alerts silent—but had written only ~40% of its usual rows due to an upstream feed degradation. The data team didn’t catch it; a business user did, hours later, when revenue dashboards dropped.

The library catches that class of silent failure immediately: the moment output volume drops below its rolling baseline, an alert fires before downstream consumers read incomplete data.


Notes: Platform vs. Domain Metrics

The Four Golden Signals answer: Did the pipeline run healthily and efficiently?
They cannot answer: Is the data mathematically and logically correct?

Domain integrity—such as financial reconciliation, or value ranges—still belongs in application-level assertions.


What’s Next

  • Data Quality: Null values, value ranges, referential integrity, etc.
  • Lineage: Shipping captured source/sink metadata to a catalog layer (OpenLineage, Unity Catalog) to map cross-pipeline dependencies.
