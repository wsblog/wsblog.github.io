Building an MLOps Velocity Tool

How we built a declarative, self-serve pipeline for feature engineering, model training, sandbox validation, and live A/B experimentation — enabling fast iterations without MLOps bottlenecks.

Jul 27, 2024 3 min read

ML Pipeline Automation

Google’s MLOps maturity model provides a helpful blueprint for automated CI/CD and continuous training:

While Level 2 is the theoretical ideal, our team pipeline made some specifics:

  1. A Feature-Centric Pipeline
    We designed our tooling to turn a “SQL query in a notebook” into an evaluated production candidate with zero boilerplate.
  2. In-Process Inference, Not a Dedicated Inference Service
    Standard reference architectures route real-time predictions to remote inference services. In low-latency services, network hops are unacceptable. We package models for in-process execution directly within the service runtime, trading runtime coupling for critical latency wins.

The Velocity Tool reframes model development as a declarative problem. The user describes the experiment they want — a feature, its source, its evaluation context — using a declarative specification:

experiment:
  feature:
    name: my_new_signal
    source_sql: |
      SELECT entity_id, value
      FROM raw.events
      WHERE event_date = '${datadate}'      
    dtype: numeric
    default: 0.0
  base_dataset: weekly_baseline
  evaluation:
    business_metrics: [primary_metric, guardrail_metric]
    backtest_window: 28d
  promotion_policy: requires_human_approval

Behind the scenes, the orchestrator automatically executes a directed acyclic graph (DAG) of containerized steps: data preparation, model training, evaluation.


Sandbox and A/B Testing

A strong offline evaluation does not guarantee success in production. So we build a two-stage evaluation before full promotion:

  1. Sandbox
    Candidate models evaluate mirrored production traffic in a shadow mode. This catches real-world regressions that offline data hides: broken assumptions, missing upstream fields, or anomalies on niche traffic segments.
  2. Controlled A/B Experimentation
    Once cleared by the sandbox, the model deploys into live production behind a controlled Pricing Experimentation rollout. Live performance is measured directly against business metrics.


The Operational Challenge

Building the pipeline is only half of the story. Monitoring live models presents distinct challenges depending on label availability:

Feedback RegimeOperational CharacteristicMonitoring Strategy
Direct LabelsGround truth arrives quickly (e.g., click vs. no-click).Direct accuracy metrics and loss tracking.
Delayed or Biased LabelsConversions or cancellations take days or weeks to settle.Proxy metrics and continuous feature distribution drift alerts.
Counterfactual SystemsThe model’s decision alters the outcome (e.g., dynamic pricing).?

Most of our production models live in the latter two regimes. A model that sets a price in a live marketplace, for example, never gets to observe what the optimal price would have been — only the outcome at the price it actually showed. The label we want is technically unobservable, and monitoring this class of system well is one of the challenging problems.
