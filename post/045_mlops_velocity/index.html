Building an MLOps Velocity Tool

How standardizing the ML pipeline let our team ship features in days instead of sprints

Last updated on Jun 26, 2026 5 min read

ML Pipeline Automation

Google’s MLOps maturity model is a useful starting point. It defines three levels — manual experimentation, partial pipeline automation, and full CI/CD/CT for ML.

These diagrams describe an ideal. Real teams have to decide which parts matter most, and where they’re willing to diverge.

Where Our Team Sits, and Where We Diverged

Our pipeline maps closely to Google’s level 2, but we diverged in two places that mattered:

  1. A custom Velocity Tool, not a generic platform.
    • Ours targets a specific shape of work: an optimization problem where most wins come from iterating on features, not from swapping out model architectures. A data scientist — or a business user with a feature idea — can take a candidate from “SQL in a notebook” to “running in production traffic” without writing pipeline glue.
  2. In-process inference, not a separate serving cluster.
    • Most reference architectures spin up a dedicated model-serving cluster. For our latency budget, that was the wrong trade-off, so inference runs inside the same backend process that serves the request. The price is tighter coupling between the model runtime and the application; the gain is a meaningful latency improvement.

The Velocity Tool

The Velocity Tool reframes model development as a declarative problem. The user describes the experiment they want — a feature, its source, its evaluation context — and the platform handles the rest: data prep, training, backtesting, packaging, and registering the result for review.

Each experiment is a DAG of containerized steps, parameterized by a single spec. Roughly:

experiment:
  feature:
    name: my_new_signal
    source_sql: |
      SELECT entity_id, value
      FROM raw.events
      WHERE event_date = '${datadate}'      
    dtype: numeric
    default: 0.0
  base_dataset: weekly_baseline
  evaluation:
    business_metrics: [primary_metric, guardrail_metric]
    backtest_window: 28d
  promotion_policy: requires_human_approval

That’s the entire surface area a user has to learn. Behind it: a Spark feature build, a training step that produces a versioned artifact, an evaluation step enforcing shared business metrics, and lineage captured for audit. Experiments run in parallel, scheduled by the platform.

The Extended Lifecycle: Sandbox and A/B Before Production

A good backtest number means very little on its own. Backtests can lie about live behaviour, and a model can be statistically “better” while still violating a business rule no one wrote down. So the pipeline has two stages between training and production:

  1. Sandbox
    • A model that passed evaluation is replayed against production data, with platform-enforced checks on the output. The point is to fail loudly on what backtests miss — broken feature assumptions, silent regressions on a data segment that matters.
  2. A/B Experimentation
    • Model from the sandbox is then deployed in production, running with a real traffic behind a controlled experiment. The user gets the same business-metric report as in training, now computed against real customer behaviour.

Promotion is a human decision, but its mechanics are fully automated. No “rebuild the artifact for production” step, no rewritten glue code. The artifact that won in A/B is the artifact that runs in production. Removing that gap closes off a long list of “almost the same code, but not quite” bugs.

The Hard Part: Knowing It’s Still Working

Detecting that a deployed model has quietly stopped doing its job is the unsolved problem of MLOps. Three regimes, not equally hard:

  • Labels are direct or cheap. Sample outputs, label them, measure performance. Solvable.
  • Labels are absent or biased. Pick a proxy metric that correlates with what you care about and monitor that — knowing the proxy will eventually drift, and you’ll have to revisit it.
  • The problem is reinforcement-shaped. The model’s own actions change the data it sees, so “compare prediction to ground truth” doesn’t apply. Monitoring becomes distributions, business outcomes, and counterfactuals rather than accuracy.

Most of our production models live in the latter two regimes. A model that sets a price in a live marketplace, for example, never gets to observe what the optimal price would have been — only the outcome at the price it actually showed. The label we want is structurally unobservable, and monitoring this class of system well is one of the challenging problems in MLOps.

Retrospective

Things from building this that I keep coming back to:

  • The spec is the product. The declarative thing a user fills in is the product. The orchestrator, storage layout, and training runtime underneath are implementation details and should be replaceable without breaking that contract.
  • Standardize the workflow The platform has strong opinions about the shape of an experiment — the spec format, the metrics, the promotion path — and stays out of the way of what goes inside it. That trade is what makes it safe for non-engineers to ship without the platform feeling restrictive.
  • Observability belongs inside the pipeline. Lineage, freshness, volume, and distribution drift are first-class outputs of every run, not a separate dashboard you build afterwards.
  • Cost should be visible to whoever decides what to run. A platform that runs hundreds of experiments a week needs to expose per-run cost to its users, not just track it internally.
