Migrating HDFS to S3 Object Storage with Zero Downtime

Aug 21, 2024 4 min read

The Legacy HDFS

A high-throughput backend service (1000+ pods serving live traffic) loaded data from on-prem HDFS. The service reads data into memory at startup and refreshes periodically in the background, while upstream Spark jobs and upload services produce and write the data.


Requirements

The task was to migrate the storage layer from HDFS to S3-compatible object storage. Constraints:

  • Zero downtime
    • Continuous availability with zero maintenance windows.
  • Decoupled lifecycles
    • Independent objects produced by separate upstream pipelines. A single synchronized cutover was not possible.
  • Zero blast radius
    • Live pricing decisions depend on these data. We have to minimize impact as much as possible.

Migration Architecture

Because HDFS reads are off the request path, we used the Strangler pattern with shadow dual-reads without risking service latency. The idea is to implement S3 read behind the existing read interface and used dynamic feature flags to route traffic and perform asynchronous parity diffing per data path.

Dynamic per-path feature flag simplified pseudocode:

enum ReadMode {
    HDFS_ONLY,    // Read only from HDFS (instant rollback)
    SHADOW_HDFS,  // Read both, compare byte hash, serve HDFS
    SHADOW_S3,    // Read both, compare byte hash, serve S3
    S3_ONLY       // Read only from S3 (post-cutover)
}

public class StorageReader {
    // ... dependencies: hdfs, s3, config

    public byte[] read(String path) {
        return switch (config.getMode(path)) {
            case HDFS_ONLY -> hdfs.read(path);

            case SHADOW_HDFS -> {
                byte[] data = hdfs.read(path); // serve HDFS
                byte[] shadow = s3.read(path);
                compareAndEmitMetrics(data, shadow);
                yield data;
            }

            case SHADOW_S3 -> {
                byte[] data = s3.read(path);   // serve S3
                byte[] shadow = hdfs.read(path);
                compareAndEmitMetrics(data, shadow);
                yield data;
            }

            case S3_ONLY -> s3.read(path);
        };
    }
}

This guarantees:

  • Instant rollback: Switch back to HDFS in seconds via dynamic config—no redeployment.
  • Granular rollout: Migrateper data path.

Migration Phases

1) Plan the Migration

  1. Inventory all data to migrate
  2. Retire obsolete data
  3. Define the migration unit
    • Scope migration per data path rather than per service

2) Build the New Implementation

  1. Consolidate reads behind a single interface
  2. Implement the S3-compatible client
  3. Add per-path dynamic feature flags
    • Toggle per path at runtime without deployments.
  4. Add shadow-read comparison
    • Read from both S3 and HDFS in parallel and emit a metric comparing byte hashes.

3) Upstream Dual-Write

  1. Enable dual-writing across producers
    • Update Spark pipelines and upload services to write to S3 object storage alongside HDFS.

4) Pilot Migration

We migrated a small, representative sample of data across different sizes and read frequencies to test the workflow and uncover issues before full rollout.

  1. Enable the feature flags
    • The service reads from both HDFS and S3, compares byte hashes, and emits diff metrics while still serving verified data.
  2. Monitor parity and the new S3 storage metrics
    • Correctness
      • Byte hash match rate
    • Reliability
      • HTTP 4xx/5xx error rates
      • Connection timeouts and socket drops
      • Client retry counts
    • Performance
      • Latency
      • Throughput

The pilot revealed two operational issues:

  • Large object download timeouts: Downloading large objects caused intermittent drops. We fixed this in Large Object Download.
  • S3 cluster instability during pod boot: The new S3 cluster had transient outages, causing pods to enter CrashLoopBackOff because loading data is required for startup readiness. We fixed this in Failsafe K8s Pod Startup.

5) Migration

With the pilot fixes deployed, we migrated all remaining data in batches.

  1. Roll out remaining paths under shadow validation

6) Cutover

  1. Disable HDFS writes, switch producers to S3-only writes
  2. Turn off HDFS shadow reads
  3. Monitor post-cutover metrics
    • Zero read/write traffic on HDFS
    • S3 storage metrics
    • Application metrics

7) Shutdown

  1. Delete legacy HDFS code & configurations

Large Object Download

During the pilot migration, small objects transferred reliably, but large objects intermittently timed out during pod startup.

Rather than building custom chunked range request logic, we switched to AWS SDK’s native CRT-based S3 client via S3AsyncClient.crtBuilder().


Failsafe K8s Pod Startup

During pilot migration, for some reason S3 storage was unstable which caused pod startup to enter CrashLoopBackOff. To eliminate this single point of failure, we moved the initial data dependency from startup time to build time: a CI step bakes a data snapshot into the Docker image, allowing pods to startup instantly from local disk before polling S3 for asynchronous updates.
